## 取得收益时，实际平均验证多少 token？

**并发 64：每请求每轮平均验证的 draft token 从 5 个降到 2.795 个，吞吐提高 6.90%；并发 128：从 5 个降到 2.646 个，吞吐提高 14.78%。** 两种方案都仍然生成完整的 5 个 draft token，联合预算缩短的是提交给 target 的验证前缀。

下表的 token 数均为**每请求、每次验证**的平均值；不是整个 batch 的总数，也不是最终接受的 token 数。

| 并发 | DSpark 平均验证 draft 数 | 联合预算平均验证 draft 数 | draft 验证数减少 | 联合预算平均验证长度（含 root） | 吞吐相对 DSpark |
|---:|---:|---:|---:|---:|---:|
| 16 | 5.000 | 5.000 | 0.00% | 6.000 | -0.29% |
| 32 | 5.000 | 4.828 | 3.45% | 5.828 | +0.48%（波动范围内） |
| **64** | **5.000** | **2.795** | **44.09%** | **3.795** | **+6.90%** |
| **128** | **5.000** | **2.646** | **47.09%** | **3.646** | **+14.78%** |

原始 DSpark 的含 root 验证长度始终为 6。把 root 也计入后，并发 64/128 的平均逻辑验证长度分别减少 **36.75% / 39.24%**。这些是提交的有效验证位置数，不包含 CUDA graph padding；不能直接解释为 GPU 计算量或耗时同比例减少。

### 统计口径与核验方式

上述均值来自各方案三轮正式测量的 `responses.jsonl`，每组 3×512=1536 个请求，**不包含预热**。对每个请求的 `meta_info.spec_cap_lens_histogram` 求和，得到长度为 $k$ 的验证次数 $H_k$。这里 $k$ 包含一个 root，因此：

$$
\text{平均验证 draft 数}
=\frac{\sum_k(k-1)H_k}{\sum_k H_k},
\qquad
\text{平均含 root 验证长度}
=\frac{\sum_k kH_k}{\sum_k H_k}.
$$

这是按“请求×验证轮次”加权的合并均值，不是先对每个请求取均值再平均，也不是三轮均值的中位数；上面的吞吐指标仍沿用三轮中位数。已经逐请求核对直方图计数之和等于 `spec_verify_ct`。联合预算在并发 16/32/64/128 下的合计请求验证轮次分别为 107266 / 107961 / 122033 / 125983。

`spec_num_proposed_drafts / spec_verify_ct` 在这些记录中始终为 5，统计的是生成的完整 draft block，**不能用它表示缩短前缀后真正提交的验证数量**。提交长度应读取上述 cap 直方图。

### 高并发下验证长度的分布

联合预算会在不同请求、不同轮次选择不同长度，并不是把每个请求固定为 2 或 3 个 draft token：

| 每请求每轮提交的 draft 数（不含 root） | 并发 64 占比 | 并发 128 占比 |
|---:|---:|---:|
| 0（仅 root） | 16.48% | 20.40% |
| 1 | 16.61% | 16.47% |
| 2 | 14.24% | 13.40% |
| 3 | 10.34% | 9.70% |
| 4 | 8.23% | 7.96% |
| 5（完整验证） | 34.10% | 32.07% |

对应的平均**接受 draft 数**，并发 64 为 DSpark 2.668、联合预算 2.233；并发 128 为 DSpark 2.683、联合预算 2.131。这说明收益不是来自每轮接受更多，而是在本次测试中，缩短验证前缀后能更快完成固定的输出工作量。实际接受数、提交验证数和生成数是三个不同指标。

## 解释与边界

- 并发 16：全部走 batch<32 回退，三轮范围与 DSpark 重叠，没有证据表明加速。
- 并发 32：只有运行 batch=32 时能启用成本决策，多数轮次回退；+0.48% 的中位数差异落在三轮波动范围内，不能当作确定收益。
- 并发 64：沿用此前 overlap 三组对照，中位数较 DSpark +6.90%、较原生 +15.10%；联合预算三轮均高于两组对照的全部轮次。
- 并发 128：联合预算三轮均高于 DSpark 和原生的全部轮次；固定工作量下有明确正收益。
- 每轮请求数固定为 512，因此并发 128 只包含约四批请求；结果包含请求补充和收尾，不能直接当成无限长稳态吞吐。
- 本轮补测吞吐和请求延迟，没有重新运行自然 EOS 准确率评测。
