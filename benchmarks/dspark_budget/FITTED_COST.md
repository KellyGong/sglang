# 拟合成本模型：和联合预算相比改了什么

本文用尽量简单的话说明 `dspark-fitted-cost` 分支相对 `dspark-joint-cost-budget`（联合预算）在计算上的区别。联合预算的完整公式见 [MECHANISM.md](MECHANISM.md)，运行方法见 [README.md](README.md)。

## 一句话

两个分支做的是同一件事：每一步决定“这一批请求总共验证多少个 draft token”。区别只在**怎么估计一步要花多少时间**：联合预算查一张逐格实测的表，本分支用一条学出来的公式，所以没见过的情况也能直接算。

## 没有变的部分

- **目标**：选一个验证预算，让“预计产出的 token 数 ÷ 这一步的耗时”最大。
- **收益的估计**：仍然用 confidence head 的置信度估计每个 draft token 被接受的概率，优先验证最有把握的。
- **draft**：每个请求每步仍然生成 5 个 draft token。预算只决定其中多少个送去验证，不会多生成。
- **计时方式**：仍然用 CUDA event 测整步的 GPU 时间。

## 区别一：一步耗时怎么估

把“一步耗时”想成寄快递的运费。

**联合预算（`cells`）是一张价目表。** 表里每一格对应一种组合：这一步有多少个请求（batch），总共验证多少个 token。每一格都要自己寄过几次才知道价钱：

- 每出现一个新的 batch 大小，都要先试 6 种预算（0、B、2B、…、5B），每种至少 3 次，凑齐了才开始按成本选预算。
- 没试过的预算，按比它大的最近一格算。
- batch 大小在运行中一直变（请求有进有出），所以不少步花在“试”上，或者因为表没凑齐而退回全部验证。小于 32 的 batch 直接不定价。

**本分支（`fit`）是一条计价公式：**

```text
一步耗时 ≈ 固定开销 + 每请求开销 × batch + 每 token 开销 × 验证图的 token 数
```

三个系数在服务运行中从所有步的实测时间里学出来，不分 batch 大小。于是：

- 新的 batch 大小不用再试，直接代入公式。
- 已经实测过的（batch，图档位）仍然用自己的实测值，公式只负责没测过的。
- 不需要逐个 batch 去试，最小定价 batch 可以从 32 降到 12。

用 8 × H20-3e 上学到的系数举例（固定 8.5 ms、每请求 0.07 ms、每 token 0.143 ms）。batch 为 16 时，验证图的 token 数 = 16 ×（1 个 root + 验证的 draft 数）：

| 每请求验证 draft 数 | 验证图 token 数 | 估计耗时 |
|---:|---:|---:|
| 5（全部验证） | 96 | 8.5 + 1.1 + 13.7 = 23.3 ms |
| 3 | 64 | 8.5 + 1.1 + 9.2 = 18.8 ms |

每请求少验证 2 个，时间省 19%。实测平均每请求验证约 3 个时，每步只少产出约 8% 的 token，所以划算。

## 区别二：预算可以取得更细

verify 的 CUDA graph 默认只有“捕获的 batch 大小 × 6”这些档位。预算落在两档之间时，实际跑的是较大的那张图，多出来的位置是白算的 padding。所以联合预算选出来的预算总是 batch 的整数倍，也就是平均每请求 0、1、…、5 个。

本分支可以额外捕获更细的档位（`SGLANG_RAGGED_VERIFY_EXTRA_TIERS`），两档之间的预算也能真正省到时间，比如平均每请求验证 2.9 个。

## 区别三：所有 rank 用同一个预算

TP8 下有 8 个 rank，每个 rank 一个进程。以前每个 rank 各自算预算。档位变细以后，并发 64 跑到约 1400 步时出现过一次卡死：所有 rank 都在等 GPU。现在由 rank 0 算好预算再广播给其他 rank，之后没有再出现。这个改动对 `cells` 也生效。

卡死的原因推断为 rank 之间置信度有极小的数值差异，选到了不同的图档位；这一点没有直接测量。

## 效果

8 × H20-3e、TP8、DeepSeek-V4-Flash-0731，每请求 256 token，3 轮取中位数。前两列是相对普通 DSpark（全部验证）的吞吐变化，最后一列是按成本选预算的步数占比。

| 并发 | 联合预算（`cells`） | 本分支（`fit`） | 定价步占比：`cells` → `fit` |
|---:|---:|---:|---:|
| 1–8 | 不定价 | 不定价 | — |
| 16 | 不定价 | +11.3% | — |
| 32 | +0.8% | +9.4% | 7% → 92% |
| 64 | +7.2% | +12.1% | 77% → 95% |
| 128 | +14.1% | +18.9% | 61% → 92% |

收益主要来自最后一列：公式让绝大多数步都能按成本选预算，而不是花在探索或回退上。并发 32 最明显，联合预算在那里基本等于全部验证。

## 怎么打开

默认仍然是 `cells`，本分支的改动都要显式打开：

```bash
export SGLANG_DSPARK_LIVE_COST_MODEL=fit
export SGLANG_DSPARK_LIVE_COST_MIN_BATCH_SIZE=12
export SGLANG_RAGGED_VERIFY_EXTRA_TIERS=2,3,...
```

完整的环境变量和运行命令见 [README.md](README.md) 的“拟合成本模型与低负载结论”一节。

## 局限

- **公式是近似**：batch 不小于 32 时，它和实测格子的中位误差约 1%；在样本少的区间（高并发运行里的 batch 12–31）会低估 8%–13%。所以实测过的格子优先用实测值。
- **系数依赖硬件**：换卡后会重新学。最小定价 batch 12 和档位列表是在 H20 上定的，换卡要重测。
- **低负载没有收益**：batch 很小时一步的时间大部分是固定开销（batch 为 1 时验证 draft token 只占约 8%），而且 overlap 模式下用的是两步之前的置信度，对少数几个请求来说噪声太大。所以 batch 低于 12 时不定价。
- **没有跑准确率评测。**
